## 1. 要解决的用户问题

用户隔一段时间回到项目时，Goal 应能回答四件事：**已经做了什么、证据在哪里、目前卡在哪里、下一步做什么**。随后 Agent 可以在明确边界内继续工作；中断、压缩或重启不能把未核验的工作变成“已完成”，也不能重复执行状态不明的副作用。

三篇帖子提供三个互补的思路：Goal 预先明确交付物和验收条件；每轮按规划、执行、评估推进；上下文变长时从持久状态重建当前任务，而非依赖聊天摘要。角色表示职责，不要求首版启动多个 Agent 或进程。帖子的成功率属于原作者报告，不能作为 TechPilot 的验收数据。

补充参考：[orchestrate-long-codex-tasks](https://github.com/fengjiayes88/orchestrate-long-codex-tasks) 是 Codex 的外部 Agent Skill（2026-10-09 查看 README 与 `SKILL.md`），以可独立验收的 Batch、依赖门、短交接和停止规则组织数小时开发任务。本文只借鉴适用于 TechPilot Goal 的任务契约；该 Skill 的 Markdown 账本、多模型路由和独立调度器不是 TechPilot Runtime 的现成能力或新事实来源。

## 3. 首版目标、边界和职责

### 3.1 首版完成标准

从新进程恢复同一个 Session 和 Goal 后，`/goal status` 能展示：Goal 目标与硬约束、计划版本、已核验阶段及依据、当前阶段、阻塞状态、建议的下一步。用户执行一步后，实际观察结果决定进度；检查失败时保留原阶段并说明下一步。最终 `/goal complete` 仍执行现有用户确认的完成条件。

### 3.2 三个职责

| 职责 | 输入 | 输出 | 首版权限 |
| --- | --- | --- | --- |
| Planner | 目标、用户验收条件、硬约束、当前阶段和已核验事实 | 有限阶段、预期证据、下一步建议或修订理由 | 可提出计划，不能修改用户条件或授权 |
| Executor | 当前阶段及已批准的普通 Tool 范围 | 一次受控 Runtime 回合与原始 Tool / Session 事件 | 继续走 Permission、Trusted Diff、C5 和 Effect Journal |
| Evaluator | 当前阶段、checkpoint、Session 工具事件及当前文件状态 | `verified / blocked / needs_review` 和具体依据 | 只读核验；不能凭模型自评写入 verified |

首版在同一个 Runtime 中实现职责边界。模型可提出计划、解释失败；Host 校验计划形状、事件引用、状态转换和可程序核验的条件。语义判断无法可靠程序核验时标记 `needs_review`，交给用户判断，不能伪装为自动通过。

### 3.3 阶段执行契约与短交接

借鉴外部 Skill 的 Batch 设计，每个 Goal 阶段在开始前至少说明：阶段 ID、所属计划版本、直接依赖、预期产物、允许触及的路径或资源、验收证据及可执行的检查方式。允许范围是工作契约，**不替代** Runtime 的 Permission、路径校验或 Trusted Diff。若阶段无法说清可观察的结束条件，先细分或标记需要用户判断，不让它进入连续执行。

每轮结束留下紧凑交接：`step_id`、checkpoint 与 Session cursor、已核验事实的事件引用、失败/阻塞、下一步建议。完整工具输出仍留在 Session/受控产物中，交接只保存索引和必要摘要；恢复时从这些事实重建状态，不将一段自由文本当作完成证明。短交接的具体长度由实际恢复质量与 Token 测量决定，不照搬外部 Skill 的固定字数。

### 3.4 不进入本轮的工作

通用多 Agent 调度、MCP、向量记忆、Skill 自进化、Fork/Rewind、Managed Run 重构、Research/M1.5 业务、跨进程分布式调度均不作为本轮前置。Context 的结构化改造先由真实失败决定；压缩只改变模型视图，不改写 Task、Session 或 Effect Journal 的事实。

## 4. 状态归属与最小协议

先写下协议和失败边界，再选具体类名。以下事件名是实施候选，不能在未核对现有序列化合同前视作已经固定的接口。

1. **Task Event 是计划与进度的事实来源。** 记录 `plan_recorded`、`step_selected`、`step_assessed`、`plan_revised` 等追加事件。计划含版本、有限且稳定的 step ID、直接依赖、阶段目标、预期产物、工作范围、验收证据和下一步提示；进度由事件投影得出，不把可变 `plan.json` 或 `STATUS.md` 当成第二真相。旧 Goal 没有计划事件时显示 `unplanned`，仍可安全恢复。
2. **Session Event 是工具请求、结果和回合事实来源。** 阶段评估引用 Session ID、Tool Call ID、Session Event ID 与 checkpoint cursor，不复制工具结果为另一份可修改账本。对当前文件的检查必须再次读取文件系统。
3. **Effect Journal 是副作用结果来源。** `started` 但终态不明时，Goal 显示 `recovery_required`；Planner、Evaluator 和自动循环均不能猜测结果、重复副作用或绕过 Host 的只读 verifier。
4. **用户 Goal 条件优先。** 模型阶段计划可以细化工作，但不能删除 `/goal criterion`、放宽 `/goal constraint`、改变 Tool 权限，或把阶段完成当作最终 Goal 完成。
5. **进度状态最小集。** 阶段使用 `pending / active / verified / blocked / needs_review`。`ready` 是“依赖均已核验、当前可选”的投影标签，`needs_evaluation` 是“已有 checkpoint、尚缺评估”的恢复提示，均不冒充已完成状态。模型说“完成了”只是 claim；只有评估通过才写 `verified`。`next_action` 是有来源的建议，不是即将自动执行的工具命令。
6. **同一 Task 的串行边界。** 计划选择、执行、评估和事件追加沿用 Task 租约；恢复时先重放并校验 Task/Session/Effect Journal，再决定下一步。
7. **依赖门与交接投影。** 只有直接依赖均为 `verified` 的阶段才可显示为 `ready`；`/goal status` 从当前 Task 投影与被引用的 Session 事实形成简短交接。没有可靠验收证据的阶段不能标为完成；但其执行是否可以重试，还须先由 Effect Journal 判定，不能简单把 `active` 改回 `ready`。

关键落盘顺序：先持久化当前计划与选中阶段 → 运行现有 Runtime 回合 → 保存绑定 Session cursor 的 checkpoint → 只读评估 → 追加阶段评估事件。若中断发生在 checkpoint 之后、评估之前，恢复应显示 `needs_evaluation` 并重做只读评估，**不得重跑执行回合**。若中断发生在副作用终态不明的位置，保持 blocker，直到 Host verifier 取得可信终态；不能由用户命令补造结果。

### G2 后续对齐：证据推进与 blocker（G2 验收冻结后）

G2 当前的 `needs_review` 与 `/goal review`、`/goal recover` 是过渡能力：它们避免模型自行猜测，但仍会把“工具到底有没有执行”“阶段是否达到验收”交给用户选择。正常产品路径不应要求用户充当日志解释器。

目标语义收敛为：

```text
工具执行、Session 事件与可验证证据留在 Thread / Runtime
        ↓
Goal 只消费 Host 已验证的结论推进阶段
        ↓
证据足够：verified 或由事实证明的 blocked
证据不足或副作用状态不明：blocked，报告具体 blocker
```

这不等同于“自动重跑”。Effect Journal 只有 `started` 而没有可信终态时，原副作用是否已经发生仍不可证明；系统保持该 Goal 的 blocker，不启动新的副作用，也不把它记成失败或成功。用户可以补充权限、恢复外部服务、改变目标或取消 Goal，但不需要回答“它算执行了吗”。Session 写入失败是另一类问题：当前 Chat 的实时显示可保持正常；当它使恢复所需证据不可信时，Goal 在后续评估/恢复时阻断，而不是让用户猜本轮结果。

实施顺序：

1. **冻结 G2 当前合同。** 先完成其独立验收，保留历史 `user_review` / `reconciled` 事件的读取和展示，不能改写旧审计记录。
2. **收回人工裁决入口。** 新 Goal 不再能通过 `/goal review verified` 把 `needs_review` 推进为 `verified`；`/goal recover` 不再是常规产品操作。兼容层只读取旧事件，新事件必须来自 Host 的确定性验证器。
3. **统一 blocker 投影。** 对“缺少验收证据”“Effect Journal 状态不明”“Session checkpoint 不可信”分别显示事实、缺失的证据与安全下一步；它们都停止该 Goal 的后续副作用，而不是假装完成或要求人工选择成功/失败。
4. **逐类增加强证据 verifier。** 只为确实可证明的工具和验收条件加入只读核验，例如受控路径下的文件内容、带身份的测试产物。正向证据可形成 Host 结论；不能证明的情形继续 blocked。不得用“文件现在存在”反推某次写入一定已完成，更不能实现通用的自动补跑。
5. **让 G3/G4 只消费已验证状态。** 自动计划、重规划和连续执行遇到 blocker 一律停在安全边界；恢复只重做只读评估，绝不因状态未知而重复副作用。

**执行进展（2026-10-10）：** 第 2 步已完成：新阶段评估只会输出 `verified` 或 `blocked`；Chat 已移除人工写入事实的入口；旧人工事件仍可回放。第 3 步现有两类明确 blocker：Effect Journal 结果不明与 Session 证据不可信，`/goal status` 分别展示原因和安全下一步。Effect Journal schema v2 的 `effect_verified` 不能再由调用方任意填写结论：目前唯一 Host verifier 会核对同一 Tool Call 的请求、Journal `started` 和 Runtime `execution_control_assessed(block)` 的身份、参数、次序及完整性，只能证明工具在委托执行前被拦截，于是记为 `not_executed`。中间损坏的 Session 事件、身份不匹配或伪造的新核验记录都不能解锁；旧 schema v1 的 `effect_reconciled` 仅供回放。即便某次未执行已获证明，若 Session 历史仍不可信，Goal 仍保持阻断。对已经进入写文件、编辑或命令执行阶段却丢失终态的副作用，目前仍没有可靠正向 verifier，绝不凭文件现状推断本次执行成功，也不自动重跑。

**Session 恢复闭环（2026-10-10）：** 上述执行前阻止证据通过核验后，若同一工具轮只有这一次请求，原始 Session 尚无对应结果且此后没有新的模型可见回合，Host 可追加一条 `TOOL_COMPLETED`：结果为已证明的 `not_executed`，并附 verifier 与原请求/控制事件 ID。原 JSONL 不改写；Effect Journal 的 `effect_verified` 仍先于补记结果持久化。恢复先检查重复结果，再追加并刷新模型历史；两个进程的恢复由同一 Session 的文件锁串行化。Session 中间损坏、结果冲突、多工具轮或后续回合已开始时不补记，Goal 保持 blocker；已经进入委托执行阶段的未知副作用也不适用此闭环。

验收应至少覆盖：

- 自由文本 `check`、模型自称完成和失败工具输出都不能被用户命令直接提升为 `verified`；
- `effect_started` 缺少终态时，恢复不重跑工具，Goal 显示可定位的 blocker；
- 有明确文件/测试证据时 Host 能自动推进，正常成对的工具事件不受影响；
- Session 持久化不可信会阻断 Goal 恢复，但不篡改实时 Chat 的已显示结果；
- G3/G4 在任何 blocker 下都不启动下一项副作用；
- 老 Goal 的历史人工事件仍能回放、审计，但不能成为新事实的伪造入口。

### G3：模型提议计划与受控重规划

- Goal setup 完成后，允许模型依据仓库事实提出 2–7 个可检查的阶段；Host 校验结构、边界与用户条件后保存。首版可先通过只读调查准备计划，计划提议本身不获得写入权限。
- 每次评估后仅在新证据、阻塞、约束变更或阶段完成时重规划；保留版本和理由。避免每轮无条件重写计划。
- 模型提议不直接授权 Tool、修改最终验收条件或宣告 Goal 成功。计划无法形成时显示具体缺口，用户仍能手工继续。

**验收：** 同一目标在资料不足、工具失败和用户约束变化时产生可解释的计划修订；旧阶段和证据可追溯，普通 Chat 不暴露 Goal 专属规划工具。

**验收结果（2026-10-10）：** 初始计划由 Goal setup 的只读提议形成；运行中阶段 `step_assessed`、用户确认的约束/验收条件变化，以及无计划 Goal 的失败工具回合可形成持久规划触发。Runtime 在 Task 租约中只开放读取/搜索和 `propose_goal_replan`，模型只能提议保留、说明缺口或给出 2–7 个结构化阶段。Host 校验依赖、已核验阶段和当前阶段后，以单条 `plan_auto_revised` 或 `plan_replan_skipped` 事件记录结果与触发 ID；旧计划版本、阶段评估和证据继续可追溯。模型不能由此修改最终验收约定或 Tool 权限。G3 专项 9/9，完整非 TUI 回归 611 passed、2 skipped；TUI 模拟仍有卡顿，不能宣称全套件通过。验收中补强 Effect Journal 的请求持久化顺序证据，详情见 [G3 受控重规划验收](../开发日志/2026-10-10-G3-受控重规划验收.md)。

### G4：有界连续执行

- 在 G1–G3 稳定后增加显式启动的连续模式；每轮仍按“选择一步 → 执行 → 评估 → 持久化”运行。
- 定义最大阶段/回合数、Token/费用观测、取消与停止原因。预算不足、权限拒绝、结果不明、`needs_review`、无进展或计划循环时停止并交付状态卡。现有 turn 级限制不能冒充完整 Goal 级费用硬上限。
- 对同一阶段的独立尝试设置有限次数；同一根因重复失败时停止该依赖分支，保留失败证据并重规划或交给用户决定。具体次数由评测和成本数据确定，不把外部 Skill 的“两次”写成产品硬规则。
- 不启动后台多 Agent；不使用模型自行重试状态不明的副作用。

**验收：** 无人逐轮按 Enter 时可推进一个受控任务；每次停止都有可恢复的下一步；取消后不再启动后续副作用。

**确定性行为验收（2026-10-10，通过）：** `/goal run` 要求已有阶段计划、最终验收条件且无待确认输入或已阻塞阶段；显式连续执行最多 4 个工作回合，普通聊天继续只推进 1 个。每轮仍执行选择、Runtime 回合、checkpoint、只读评估与必要的重规划。模型替换计划、阶段失败、结果不明、中断、无进展和 Runtime 限额均停止；规划回合触及限额也不得启动下一阶段。连续模式对同一阶段最多接受 2 条历史选择记录作为当前保守保护阈值，受阻后不自动重试；具体尝试策略仍需 G5 的失败样本与成本数据校准。`goal_run_stopped` 追加式 Task 事件记录停止原因、工作回合数和 Provider 可观测的 Token/估算费用，状态卡给出恢复下一步；Session/Effect Journal 证据不可信时保持 fail-closed。Token/费用不是 Goal 级硬预算。G4 定向 13/13、仓库非 TUI 回归 624 passed、2 skipped、Ruff 通过；TUI 模拟未纳入本轮。确定性验收覆盖多阶段完成、四回合上限、预算触顶、规划触顶、首笔写入后取消阻断下一笔写入、未知副作用、无进展、计划替换和损坏停止事件；真实模型效果属于 G5。

### G5：真实任务评估，再决定 Context/Memory

- 固定至少一个正常多阶段 Coding 任务、一个中断恢复任务和一个失败/约束变化任务；在运行前固定验收与预算。确定性 Runtime 结果和真实模型成功率分开报告。
- 观察阶段完成率、错误完成声明、重复工具调用、人工介入、Token、耗时、压缩/重启后的下一步准确性。真实模型任务不以帖子里的数字当目标。
- 若观察到压缩导致关键任务事实丢失，再改 Goal 上下文投影；若发现能力失败样本和独立评测，再排 Skill 自进化。

**验收：** 有可复现实验记录、失败归因和下一切片依据；能演示跨进程中断后从原 Task/Session 准确继续。持续闲置一天是额外稳定性观察，不是恢复能力的必要条件。

**第一切片（2026-10-10 起，开发中）：** `benchmarks/goal_model_v0/deck.json` 固定同一 CLI 数据导出任务的正常、首阶段后跨进程恢复、首阶段后新增约束三例，列明初始文件、两阶段计划、允许修改的路径、外部功能判据和每回合/试运行协议上限。`techpilot/evaluation/goal_model_v0.py` 可核对题卡与样例字节摘要、准备三份隔离工作区、按冻结合同无模型初始化 Goal，并从持久 Task/Session/Effect Journal 只读采集阶段与用量快照；`goal_model_oracle.py` 从候选文件快照独立验收 CLI 输出、文档和冻结文件。准备、初始化、采集和验收均不调用模型；真实执行由独立的受限 Chat 驱动器完成。三例共用同一代码基底，只用于比较运行方式，不代表一般任务成功率。使用说明见 [Goal model pilot v0](../../benchmarks/goal_model_v0/README.md)。

**验收器校准（2026-10-11）：** 本地定向 7/7 通过，覆盖未改样例应失败、三例正确参考实现应通过、Unicode 转义在约束案例应失败、冻结文件或允许范围违规应失败、同名记录不能覆盖，以及评分前后候选工作区内容不变。仅证明外部判据能区分这些已知样本，不代表真实模型任务已成功。执行记录协议另有 5 项定向校准，合计 12/12 通过；完整试评合同见 [README](../../benchmarks/goal_model_v0/README.md)。

**执行记录入口与真实试评（2026-10-11）：** `goal_model_v0.py` 的快照新增批次、Checkpoint 增量和约束原文，`goal_model_protocol.py` 把每个阶段边界绑定到既有快照与外部验收，追加摘要链记录，核对 Task/Session 身份、跨进程恢复、约束接受、试运行批次与工作回合上限，并分开记录外部报告用量和 Runtime 可观测用量。预算复核只给停止或人工复核提示；报告分别呈现 Goal 自评与外部验收，并显式列出缺失证据。协议入口定向 5/5 通过。`glm-5.3` 三例外部验收 2 通过、1 失败，三例 Goal 均未自行完成；同日跨进程恢复准确。隔天等待是试评自行加设的条件，用户指出其并非技术前提后，试评立即恢复，保留原协议的 24 小时缺项，未宣称原协议验收通过。已知 Token 下界 655,735。失败样本证实 README 的 CRLF 文件与模型 LF 跨行编辑请求不匹配；可信 Diff 随后加入纯 CRLF 且唯一匹配时的保守兼容，不追改本次成绩。新的[单例模型回归](../../benchmarks/goal_model_v0/CRLF-REGRESSION-2026-10-11.md)观察到 README 编辑与外部验收通过，但 Goal 因试评权限拒绝命令和冻结测试写入仍阻塞。下一步先使模型可见的评测合同与权限一致，再评估 Runtime 的阶段恢复语义。原三例明细见 [G5 阶段记录](../../benchmarks/goal_model_v0/PILOT-2026-10-11.md)。

## 7. 兼容与风险检查

- 新事件必须向后兼容：旧 Goal 无计划事件也能显示/恢复；损坏或无法核对的进度事件不能投影成 `verified`。
- Task checkpoint、Session cursor 与阶段评估跨文件并非单个事务；按第 4 节的落盘顺序和恢复规则处理断点。
- `GoalPlan` 是工作顺序，不是 Permission 或副作用授权。写入仍由原 Tool Executor 和 Trusted Diff 控制。
- 外部 Skill 用文件账本与新 Agent 上下文做交接；TechPilot 保留现有 Task/Session/Effect Journal 事实归属，不复制其 Markdown 文件结构、固定模型路由、调度器轮换频率或无证据重试规则。
- 计划正文和第三方资料属于不可信输入；Host 校验形状与权限，不能把模型文本当系统指令。
- 文件存在、命令退出 0 只能证明对应检查通过；代码质量或结论语义仍可能需要独立测试或人工评估。
- 不覆盖其他工作区改动，不碰冻结 M0 Holdout，不把旧 Legacy 双账本接回新 Goal。
