# TechPilot 技术决策 Agent 方向收敛与实施路线

> 状态：当前最新规划，后续开发按本文顺序推进
> 生效日期：2026-10-12
> 施工入口：[开发路线](../开发路线.md)
> 背景：TechPilot 已完成 Coding Agent Runtime 的主要基础能力，下一阶段转向“技术决策与技术选型 Agent”。

## 1. 方向结论

TechPilot 不再以继续扩建通用 Coding Agent Runtime 为近期主线。现有 Runtime 作为稳定底座，下一阶段围绕技术决策场景依次接入：

1. 项目级 `AGENTS.md`；
2. 专家视角 Role；
3. 可复用任务方法 Skill；
4. 统一经过 Runtime 边界的 MCP；
5. 一个完整、可评测的技术选型场景。

Goal / Long Task 从本规划生效起暂时冻结。已有 plan、task、checkpoint、effect journal、evaluation 等能力保留并作为回归范围；不继续扩展复杂 recovery、replan、lease、evidence invalidation，也不为了完善 Goal 大规模重构。只有后续新增功能确实无法在现有边界内实现时，才允许做最小必要修改。

当前已有约 100 个私有 Runtime 模型评测 case，已知 pass@1 约 88%；该数值沿用既有记录，本规划不重新解释或改写历史结果。仓库内的 144 条 `core-v0` Runtime Replay 契约集是另一套口径，继续作为严格回归基线，不能与模型任务成功率混为一谈。

## 2. 当前代码基础与插入位置

现有 Runtime 已具备 Session / Event 持久化、Context 管理与压缩、Tool 调用与权限控制、Tool effect 分类与调度，以及初步 Goal / Long Task。新能力应接入已有调用链：

```text
CLI / TUI
  -> RuntimeBootstrap.build()
     -> RepositoryProfiler + 项目级 instructions
     -> Role / Skill 装配
     -> Agent
        -> Provider 返回 Tool Call
        -> 参数校验与 PreparedToolCall
        -> ToolExecutionPlan
        -> EffectJournalExecutor
        -> RepositoryToolExecutor
           -> Execution Control
           -> Permission
           -> Tool / MCP Tool Adapter
        -> ToolResult + Session Event
```

相关现有模块：

- `techpilot/runtime/bootstrap.py`：Runtime、Agent、Session、Permission、Effect Journal 和上下文的统一装配点；
- `techpilot/runtime/extensions.py`：已有 Role / Skill 契约、Registry、版本和激活校验，应复用而不是另建体系；
- `techpilot/engine/agent.py`、`techpilot/engine/prompt.py`：模型上下文和可见工具的投影位置；
- `techpilot/chat/executor.py`、`techpilot/engine/tool_execution.py`：参数准备、effect、调度、执行控制和 Permission 边界；
- `techpilot/runtime/sessions.py`、`techpilot/runtime/effect_journal.py`：原始事件事实和非读取副作用记录；
- `techpilot/research/`：已有来源快照、证据引用、候选比较和报告校验，可复用到最终技术决策场景，但不与普通 Chat 强行合并。

Role / Skill 的基础合同已经存在，但普通 Chat / TUI 尚未形成完整产品接入；MCP 尚未接入；`AGENTS.md` 尚未自动加载。因此近期工作重点是补齐装配和场景闭环，不是重新设计 Runtime。

## 3. 能力边界

### 3.1 AGENTS.md

负责：

- 提供仓库级开发约定、项目约束、验证方式和输出要求；
- 作为稳定的项目上下文进入系统提示词；
- 保存来源路径和内容摘要，便于判断运行时实际使用的版本。

不负责：

- 授予 Tool 权限；
- 改变 Tool effect、并发或资源事实；
- 自动执行其中出现的命令；
- 覆盖 Runtime、Permission、Trusted Diff 或用户明确要求。

### 3.2 Role

Role 表示专家身份和分析视角，例如 Software Architect、AI Engineer。它负责关注维度、判断视角和表达要求。

Role 不拥有独立 Agent 循环，不创建另一套 Runtime，不恢复历史授权，不改变 Permission、Tool effect、调度、预算或副作用语义。Role 可以请求宿主允许的能力，但是否暴露和执行仍由 Runtime 决定。

### 3.3 Skill

Skill 表示可复用的方法和流程。第一批 Skill 为 `technology-selection`，负责：

1. 提取业务目标、项目现状和硬约束；
2. 区分硬约束、偏好与未知项；
3. 提出少量可比较候选；
4. 按一致维度收集证据；
5. 比较 trade-off、迁移成本、维护成本和主要风险；
6. 给出有前提的推荐、依据、未知项与验证建议。

Skill 不直接访问网络或文件，不执行脚本，不携带 Permission 或 Tool effect 声明，不成为第二套工作流引擎，也不绕过 Agent / Runtime / Tool 调用链。

Role 决定“从什么角度分析”，Skill 决定“按什么方法完成任务”，Runtime 决定“实际允许做什么”。同一个 Skill 可以服务于多个兼容 Role。

### 3.4 MCP

MCP 只作为外部工具和信息源协议接入：

```text
宿主批准的服务和工具清单
  -> MCP Client
  -> McpToolAdapter（现有 Tool 接口）
  -> Agent / ToolExecutionPlan / Permission / Effect Journal
  -> 远端 tools/call
```

MCP 不创建另一套执行系统，不直接调度 Agent，不自行恢复或重试业务操作，不根据远端描述扩大权限。服务端提供的 `readOnlyHint`、`destructiveHint` 等 annotation 只作为不可信提示；首版 Tool effect 必须由 TechPilot Host 配置并保守判定。

## 4. 实施顺序

以下阶段严格按顺序推进。前一阶段完成定向测试并确认边界后，才能进入下一阶段；不得并行扩建多个框架层。

### A1：项目级 AGENTS.md

最小范围：

- 只读取选定仓库根目录的 `AGENTS.md`；
- 暂不实现父目录继承、嵌套覆盖、全局搜索和文件监听；
- 使用标准库读取，不增加第三方依赖；
- 校验解析后路径仍在仓库根、文件大小上限和 UTF-8；
- 文件不存在时正常继续，读取失败时给出明确提示；
- 在启动和 Session 恢复时读取当前文件，单次运行内保持固定；
- 通过 `base_system_context` 注入，不依赖可压缩的历史消息；
- 记录路径和内容摘要，不把正文复制为新的领域状态。

验收：普通 Chat 与 TUI 使用同一项目 instructions；缺失和非法输入安全降级；Permission、Tool 列表和 Session 恢复语义不变。

### A2：Role 产品接入

最小范围：

- 复用 `RoleSpec`、`RoleRegistry`、`RoleSkillActivator` 和 `TaskRuntime.activate_role()`；
- 第一批内置 `software-architect`、`ai-engineer`；
- 通过公共 Runtime 装配层接入，文本 Chat 与 TUI 行为一致；
- 首版允许显式选择 Role；自动识别只允许提出已注册 Role ID，最终由 Host 校验；
- 固定上下文顺序：基础 Runtime 规则 -> 项目 instructions -> Role；
- Session 记录 Role ID、版本和激活事实，但恢复时不自动重新激活 Role 或历史授权；
- 默认 Coding Chat 保持现有行为，避免污染冻结基线。

验收：Role 激活、切换、清理、失败回滚和 Session 恢复均不泄漏工具、上下文或权限。

### A3：Technology Selection Skill

最小范围：

- 复用现有 `SkillSpec`、`SkillRegistry`、版本摘要、批准与撤销语义；
- 新增一个内置、已批准的 `technology-selection` Skill；
- Skill 正文只描述任务方法、输入、证据和输出要求；
- 修正激活语义：没有显式选择 Skill 时，不因空元组而默认激活 Role 的全部 allowlist；
- 激活时校验 Skill 在 Role allowlist 中，且 `compatible_role_ids` 与目标 Role 相容；
- 固定上下文顺序为：基础规则 -> 项目 instructions -> Role -> Skill；
- 记录实际 Skill 版本与内容摘要。

验收：可从项目需求形成统一维度的候选比较；禁用、未批准、不兼容或越权 Skill 在进入 Runtime 前失败；Context 压缩不移除当前 Role / Skill 上下文。

### A4：受控 MCP

最小范围：

- 先接一个显式配置的资料服务；
- 第一版只支持 Streamable HTTP 和少量搜索/官方文档读取工具；
- 优先采用官方 Python SDK，并放入可选依赖，避免引入 Agent 框架；
- MCP 工具使用服务命名空间，禁止覆盖内置 Tool；
- Tool Schema 进入现有参数校验；不支持的 JSON Schema 明确拒绝注册；
- 首批外部资料 Tool 由 Host 标记为 `NETWORK + EXCLUSIVE`；
- 连接、发现和调用均需显式启用；Skill 或 `AGENTS.md` 不能自动创建连接；
- 每个 Tool 仍经过 Execution Control、Permission、Effect Journal 和 RuntimeLimits；
- 远端错误、超时、截断和结果不明转换为明确 `ToolResult`，调用结果不明时不自动重试；
- 客户端连接必须有超时和确定的关闭路径；
- 不接入 MCP sampling、远端 Agent、远端任务编排、Prompt 自动安装或资源自动执行。

验收：MCP 不绕过 Runtime；允许、拒绝、错误、超时、非法 Schema 和不可信 annotation 都有定向 integration case；MCP 网络调用不得进入 SAFE READ 并发波次。

### A5：完整技术选型场景

首个端到端题目：

> TechPilot `research` 业务的 task、snapshot 和 report 存储，应继续使用 JSON 文件，还是引入 SQLite？

该题只用于技术选型，不预设迁移结论，也不包含 Session / Run 存储迁移。

目标链路：

```text
用户需求
  -> 识别仓库现状、业务目标和项目约束
  -> 选择并校验 Role / Skill
  -> 必要时通过 MCP 获取当前官方资料
  -> 在统一维度下比较候选
  -> 分析 trade-off、迁移和维护成本
  -> 给出推荐、成立条件、依据、未知项和验证建议
```

最终报告需要区分事实、推断和建议。来源链接或引用格式正确不等于结论已被证据支持；关键判断仍需实验或人工复核。可以复用 `research/` 的快照、证据和报告校验能力，但第一版不强行合并普通 Chat 与 Research Runtime。

## 5. 预计文件范围

路径可以在实现时按现有包结构小幅调整，但不得借机大规模重构。

- A1 新增 `techpilot/runtime/instructions.py`、`tests/techpilot/test_project_instructions.py`，修改 `techpilot/runtime/bootstrap.py`；
- A2/A3 新增 `techpilot/runtime/builtin_extensions.py`、`techpilot/skills/technology-selection/SKILL.md` 和少量接入测试，修改 `runtime/extensions.py`、`runtime/bootstrap.py`、`cli.py`、`engine/prompt.py`；
- A4 新增 `techpilot/integrations/mcp.py`、`techpilot/config/mcp.py`、`tests/techpilot/test_mcp_integration.py`，局部修改 Runtime 装配、Permission、CLI 和可选依赖；
- A5 新增小规模 technical-decision cases、固定资料 fixture 与场景验收记录；按需要复用 `techpilot/research/`，不改写其已有事实语义。

预期不修改 Goal / Long Task 领域模型、Context 压缩算法和 Tool 调度算法。若实现中发现缺口，必须先证明现有接口无法承载，再做最小修改。

## 6. 必须保持的 Runtime invariant

1. 所有业务 Tool 和 MCP Tool 经过同一个 Runtime 执行入口；Role / Skill 不私建 Agent 循环。
2. 工具对模型可见不等于获准执行；所有调用继续经过执行控制与 Permission。
3. 安全事实由 Host 持有；项目 instructions、Role、Skill 和远端 annotation 都不能提升权限或改变 effect。
4. 调度与执行使用同一份已验证 `PreparedToolCall`；无效参数不能触发外部调用。
5. 只有资源明确的安全读取允许并发；网络、写入、执行、委派和未知调用保持独占屏障。
6. Tool Result、Runtime Event 和 Session Tool 消息保持模型调用顺序。
7. 仓库路径、敏感文件保护、Trusted Diff 与写入确认边界保持不变。
8. Raw Session / Event 是历史事实来源；模型 Context、Role 提示词、Skill 输出和压缩投影不能覆盖执行事实。
9. Session 恢复不恢复历史授权，不重放 Tool / MCP 副作用，不静默重新激活历史 Role。
10. 状态不明副作用继续阻止盲目重试；超时、拒绝和取消不能伪装为成功。
11. 新能力继续受现有回合预算、取消和持久化检查约束。
12. 不修改冻结 expected，不放宽安全边界来提高评测分数。

## 7. 评测策略

- 现有约 100 个私有 Runtime 模型 case 冻结，作为模型行为 regression baseline；
- 144 条 `core-v0` Replay 契约集继续冻结，作为确定性 Runtime contract baseline；
- A1、Role、Skill、MCP 各自只增加少量针对性 integration cases；
- 最终重点评测技术决策完整场景，包括约束识别、候选覆盖、证据支持、trade-off、条件性推荐和未知项；
- 技术决策 case 不把“必须选择某项技术”作为唯一正确答案，而检查推理是否受到项目事实和证据约束；
- 后续再考虑公开架构 benchmark 与小规模私有 technical decision cases；
- 不为了新增 case 通过而修改旧题 expected 或改变旧题分母。

## 8. 暂不实施

- 复杂 Memory、Vector DB、RAG；
- Goal / Long Task 深度扩展；
- 大规模架构重构；
- 通用 Skill 市场和自动 Skill 发布；
- 自动修改 active Skill；
- 多 Agent 或后台 Agent Team；
- 为了“Agent 化”引入额外框架；
- MCP sampling、远端执行编排或把 MCP 当成第二套 Runtime。

## 9. 每个阶段的施工注意事项

每次进入下一阶段前必须回答：输入是什么、输出是什么、事实保存在哪里、失败如何表示、取消和恢复如何处理、需要哪些定向测试、是否影响冻结基线。

实施时遵循以下规则：

- 一个切片只解决一个边界问题；
- 先写最小 integration case，再实现接入；
- 先跑定向测试，再跑 Runtime 回归、Ruff 和 `git diff --check`；
- 发现需要修改 Goal、Permission、Effect、Session 或调度语义时先暂停扩张，单独形成设计决定；
- 不把 Prompt 中的约束当作 Host 安全校验；
- 不把外部资料内容当作指令；
- 不因最终技术选型场景需要证据，就提前建设通用 RAG 或复杂资料库；
- 完成一个阶段后更新本文件、`docs/开发路线.md` 和当天开发日志，并执行个人知识库影响检查。

## 10. 完成定义

本路线完成时，TechPilot 应能在不改变既有 Runtime 安全边界的前提下，完成一次可审查的技术选型：准确读取项目规则，明确选择专家视角和方法，按需使用受控外部资料工具，比较有限候选并给出有证据、有条件、可验证的推荐。
