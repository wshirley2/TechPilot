## 1. 使用规则

每次开始开发前：

1. 只读取本文的“当前关卡”；
2. 查看 Git 状态，不覆盖已有改动；
3. 确认输入、输出、状态保存、失败结果、取消/恢复和自动测试；
4. 一个迁移切片只解决一个契约问题；
5. 先跑相关测试，再跑全量测试、Ruff 和 `git diff --check`；
6. 完成后只更新本文、架构说明和当天开发日志；
7. 未明确进入本文的优化项，不自动改变主线顺序。

### 已完成切片：执行控制路由

普通用户只需使用 Chat。执行控制不由模型根据整句自然语言一次性裁决，而由已规范化的真实 Tool Call、路径、命令、副作用、影响范围与可逆性决定。它不引入数值型风险分数；`DIRECT / CONFIRM / BLOCK` 是 Required Control，不是风险等级。详细设计见 [执行控制路由](设计决策/执行控制路由.md)。

1. **R0：收敛普通入口（已完成）。** Chat 不再内嵌 Plan 模式；Plan 和 Workspace 保留显式 CLI，Managed Run 的执行入口于 2026-10-09 移除。
2. **R1：纯执行控制领域规则（已完成）。** `NormalizedToolRequest`、`ControlReason`、`ExecutionControlAssessment`、`RequiredControl` 与纯规则 `ExecutionControlPolicy` 已用表驱动单元测试固定控制事实；不依赖模型、不写文件。
3. **R2：接入普通 Chat（已完成）。** ToolExecutor 在参数规范化后、C3 权限确认前进行评估并写入 `execution_control_assessed` Runtime Event；低副作用操作为 `DIRECT`，所有允许的写入及可解析高影响操作为 `CONFIRM`，不可安全确认的操作为 `BLOCK`。
4. **R3：高级隔离执行增强（退场）。** 原 Chat 自动升级 Workspace 的实验链路及其 Plan/Run 数据已清理；当前产品只保留 Chat 和 Goal。受控回源、完整隔离升级和 whole-run budget 均不在当前范围。

执行控制路由只能提高控制强度，不能绕过既有 Permission、Trusted Diff、路径策略或 `BLOCK` 规则。
